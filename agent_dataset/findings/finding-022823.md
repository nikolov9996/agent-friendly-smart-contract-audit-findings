# A malicious executor can delete the fees been

## Description

The contest README states that the executor of ArrakisStandardManager is a RESTRICTED role during rebalance action on vaults. ArrakisStandardManager::rebalance() with a malicious payload, which ends up stealing the accrued manager fees and re-depositing them into the pool’s liquidity. On calling rebalance(), it makes a call to the module, with provided payloads_ from the executor: (bool success,) = address(module).call(payloads_[i]); For this attack, the payload’s function signature will be of the swap() function in the ValantisHOTModule. The swap() function essentially does these 3 things: 1. Withdraw liquidity from the pool (via ALM) 2. Do an arbitrary call to an arbitrary address (router_.call(payload_)) 3. Deposit the resulting balance back into the pool (via ALM) The intended functionality is that in step 2, a call is made to a router which swaps the tokens to rebalance the funds. However, a malicious executor can use this arbitrary call to execute any admin function in other contracts (HOT, SovereignPool) that only this module is allowed to call. The issue with the above is that the swap() function has a slippage check after step 2: if (zeroForOne_) { if (balance1 < _actual1 + expectedMinReturn_) { // require(balance1 >= _actual1 + expectedMinReturn_); revert SlippageTooHigh(); } } else { if (balance0 < _actual0 + expectedMinReturn_) { revert SlippageTooHigh(); } } This means that in order for the swap() to not revert, the balance of the output token must increase by at least expectedMinReturn_ during step2. Now due to the _checkMinReturn check that is done at the start of swap(), the expectedMinReturn_ must be at least 1. Hence, in step 2, trying to call admin functions like HOT.setFeeds() will revert since no tokens are sent in to the contract during this call, so it fails the slippage check shown above. This is the case for most admin functions except for two, one of which is SovereignPool.claimPoolManagerFees: ```solidity function claimPoolManagerFees( uint256 _feeProtocol0Bips, uint256 _feeProtocol1Bips ) external override nonReentrant onlyPoolManager returns (uint256 feePoolManager0Received, uint256 feePoolManager1Received) { (feePoolManager0Received, feePoolManager1Received) = _claimPoolManagerFees( _feeProtocol0Bips, _feeProtocol1Bips, msg.sender ); } ``` We can see that the pool manager fees are sent to msg.sender which is the module. This will increase the module’s balance during step 2, allowing it to pass the slippage check. Then, these claimed manager fees will be deposited back to the pool in step3, effectively deleting the accrued manager fees. (All of this is proven in the coded PoC) In addition to the above fund loss, since poolManager is updated to address(0), any onlyPoolManager functions within the pool will revert. 100% of the fees which are meant for the Arrakis manager are re-deposited into the pool by a malicious executor and never claimable by the manager.

## Recommendation

Don’t allow the router_ parameter in ValantisModule to be the SovereignPool associated with this module. + if (router_ == address(pool)) revert();

## Derived Narrative

The following field is derived content and may not be source-grounded:

The vulnerability is an economic manipulation that allows a malicious executor of the ArrakisStandardManager contract to delete the fees that are accrued for the pool manager. The root cause is that the ValantisHOTModule.swap function accepts an arbitrary router address and payload, then performs three steps: it withdraws liquidity from the pool, executes the supplied payload via a low‑level call to the router, and finally deposits the resulting token balance back into the pool. A slippage check is performed after the payload execution, requiring the output token balance to increase by at least the expected minimum return, which is forced to be at least one unit. Most admin functions called through the router would fail this check because they do not transfer tokens, but the SovereignPool.claimPoolManagerFees function does transfer the manager fees to the caller (the module). When a malicious executor includes a payload that calls claimPoolManagerFees, the module receives the fees during step two, satisfying the slippage condition, and then re‑deposits those fees into the pool in step three. As a result, the fees that should be claimable by the pool manager are effectively erased from the manager’s balance and become part of the pool’s liquidity. Additionally, the poolManager variable is set to address(0) during the attack, causing any function protected by the onlyPoolManager modifier to revert, which breaks expected pool management operations. The issue occurs during a rebalance transaction where the executor role, although described as restricted, can supply a malicious payload. It is hard to notice because the rebalance call succeeds, no revert is emitted, and the pool’s token balances appear normal while the manager’s fee accounting shows a zero balance. The impact is loss of all accrued manager fees for the affected vault and disruption of pool manager functionality. The vulnerability was discovered through manual audit and a proof‑of‑concept test that demonstrated the fee‑stealing flow. To fix the issue, the module should reject any router address that points to the pool it is managing, preventing the module from calling claimPoolManagerFees on its own pool, and the design should enforce that only legitimate swap operations that respect accounting invariants are allowed. This class of bug falls under unchecked external calls with insufficient validation of side‑effects, leading to unauthorized fund redirection and accounting violations.
