# Potential overwriting of auction storage leading to loss of auctioned tokens

## Description

The ApiologyDAOAuctionHouse contract utilizes random numbers generated by the Pyth Entropy contract to create auctions for the queued tokens. When a random number is ready to use, the ApiologyDAOAuctionHouse::entropyCallback function is invoked to handle the response and initiate the auction creation process.
File: ApiologyDAOAuctionHouse.sol
```solidity
358: function entropyCallback(
        uint64 sequenceNumber,
        address _providerAddress,
        bytes32 randomNumber
    ) internal override {
359:     emit RandomNumberReceived(sequenceNumber, randomNumber);
360:     _createAuctionWithRandomNumber(randomNumber);
361: }
```
The problem arises when the ApiologyDAOAuctionHouse::entropyCallback function is called while there is an ongoing auction. This behavior could result in the auctionStorage being overwritten, leading to the loss of previously registered auction data.
File: ApiologyDAOAuctionHouse.sol
```solidity
378: function _createAuctionWithRandomNumber(bytes32 randomNumber) internal {
415:     auctionStorage = AuctionV2({
416:         apdaoId: uint96(apdaoId),
417:         clientId: 0,
418:         amount: 0,
419:         startTime: startTime,
420:         endTime: endTime,
421:         bidder: payable(0),
422:         settled: false
423:     });
426: }
```
Consider the following scenario:
1. The owner calls the pause function and settles to close the current auction.
2. The owner calls the unpause function, triggering a call to ApiologyDAOAuctionHouse::requestRandomNumber, which invokes Entropy::requestWithCallback.
3. The owner once again calls pause and unpause, triggering another call to ApiologyDAOAuctionHouse::requestRandomNumber, which invokes Entropy::requestWithCallback.
4. Finally, entropy calls ApiologyDAOAuctionHouse::entropyCallback twice, resulting in the auctionStorage being overwritten.
It is important to emphasize that the call to the ApiologyDAOAuctionHouse::entropyCallback function occurs in a separate transaction. Once the random number is ready to use, the entropyCallback function will be called by the Entropy contract. This happens in a separate transaction submitted by the requested provider. On the other hand, we must not assume that entropy will not call the callback multiple times.
This results in a situation where the auctionStorage is overwritten, causing the token that is currently in the auction to be lost, including the associated bid amount.

## Proof of Concept

No poc.

## Recommendation

Before creating a new auction, check the current state of the auctionStorage to ensure that there is no ongoing auction.
```solidity
function entropyCallback(
    uint64 sequenceNumber,
    address _providerAddress,
    bytes32 randomNumber
) internal override {
    emit RandomNumberReceived(sequenceNumber, randomNumber);
    if (auctionStorage.settled) { 
        _createAuctionWithRandomNumber(randomNumber); 
    }
}
```

## Derived Narrative

The following field is derived content and may not be source-grounded:

The vulnerability consists of an unchecked overwrite of the contract's auction storage when the entropyCallback function is invoked while a previous auction has not been settled. The contract relies on a random number supplied by an external Entropy contract to initialise a new auction; the callback creates a fresh AuctionV2 struct and assigns it directly to the single auctionStorage variable. Because the code does not verify that the existing auction is settled before writing the new struct, a second callback – which can be triggered in a separate transaction if the Entropy provider calls back more than once or if the owner repeatedly pauses and unpauses the contract – overwrites the previously stored token identifier, bid amount and other auction parameters. This race‑condition‑like behaviour leads to the loss of the token that was being auctioned and the associated bid funds, effectively making the funds disappear from the protocol's perspective. The issue manifests when the contract is unpaused, a random‑number request is pending, and the Entropy contract invokes the callback before the earlier auction has been marked as settled. Users experience a missing or empty auction UI, see a zero balance for the token they expected to be sold, and cannot retrieve their bid because the stored data has been erased. The problem was identified during a security audit that examined the flow of entropyCallback and noticed that the function does not guard against multiple invocations. It is hard to notice because the overwrite occurs silently without emitting an explicit error event; the contract simply presents a new, empty auction. The bug belongs to the class of state‑overwrite or race‑condition vulnerabilities where a critical storage slot is rewritten without proper state validation. To remediate, the callback should first check that the current auctionStorage is settled (or otherwise inactive) before creating a new auction, or the contract should employ a re‑entrancy guard, separate storage per auction, or a one‑time‑only flag to ensure the callback cannot be executed twice for the same request. This prevents the accidental loss of auctioned tokens and preserves the integrity of the bidding process.
