# LV token holders receive proportional fees incorrectly

## Description

The Corc protocol claims that the LV token holders should accrue fees that the protocol generates, from the docs: In our design we envision several mechanisms through which the Liquidity Vault will generate revenues. Some of these are from protocol fees that will flow to the Liquidity Vault and accrue to Liquidity Vault tokenholders. However, the fee accrual is incorrect, a user can deposit just before fees are about to be distributed to LV holders, and still receive the same amount of fees as a user who deposited tokens in the beginning. There is one LV token per RA:PA pair, however the CT and DS tokens expire and there may be several CT and DS tokens issued by the protocol. Users can mint an LV token via the Vault::depositLv() function, by depositing the corresponding RA asset. The first issue is that if User A mints a LV token, and request to redeem it, then some fees from swapping in the AMM pair for the CT and RA token are generated, or the protocol collects fees from users utilizing its functionality, then a User B mints a LV token, and request to redeem it, both users will accrue the same amount of fees generated by the protocol, when this shouldn't be the case. As the first users has had his request for redeem for a much longer period, risking the price of the RA token dropping significantly, while User B may just call the Vault::depositLv() function the last block before the CT and DS tokens expire, and request a redeem immediately. Then in the next block when the CT and DS tokens have already expired he can claim the same amount of fees as User A, this is demonstrated in the first POC. To better illustrate the second problem consider the following example  
• User A and User B minted LV tokens while the first issued CT and DS tokens were still not expired  
• The UniV2 pair generated some fees  
• The protocol collects fees, from users utilizing its functionality  
• The issued CT and DS tokens expired  
• The protocol issued new CT and DS tokens  
• User C mints some LV tokens  
• The UniV2 pair generates some more fees,  
The fees will be split equally between all the users (of course taking into account the amount of LV tokens they hold).  
The protocol doesn't implement any mechanism to track when users minted LV tokens, or when they requested a redemption of their LV tokens, or what rewards were accrued to the current LV holders.

External pre-conditions  
Attack Path  
Fees are distrusted incorrectly, users who have held LV tokens since the beginning will receive an equal amount of fees with users who deposit much later, even if no fees are generated by the protocol since the last user deposited. The last users to deposit are effectively stealing fees from the users who deposited earlier.

## Derived Narrative

The following field is derived content and may not be source-grounded:

The vulnerability is an incorrect fee accrual mechanism for the Liquidity Vault (LV) token. The contract distributes protocol fees to LV token holders without taking into account when each holder minted or redeemed their LV tokens. Because the system does not record a snapshot of fee balances at the moment a user deposits, any fee that is added to the underlying AMM pair or collected by the protocol is divided equally among all existing LV tokens, regardless of how long each holder has owned them. An attacker can exploit this by waiting until the last moment before a fee distribution or before the CT/DS tokens expire, depositing a new LV token, immediately requesting redemption, and then claiming the same amount of fees that early depositors would have earned. The impact is that early participants receive a reduced share of fees, while late participants effectively steal fees that should belong to the former. This occurs whenever fees are generated after a user has already deposited but before a new user deposits, and the protocol does not update per‑holder accounting. All LV token holders, the protocol’s revenue model, and any user relying on the promised proportional fee share are affected. The issue was discovered during an audit by injecting synthetic fees into the Uniswap V2 pair and observing that two users who deposited at different times received identical WETH balances after redemption. The bug is subtle because the UI shows a simple “fees per LV token” figure and does not expose the missing time‑weighting, making the unfair distribution easy to miss. The correct fix is to introduce a per‑holder fee accounting scheme, such as maintaining a cumulative fee per token snapshot at each distribution, updating individual balances on deposit and redemption, or using a checkpoint system that records the fee index at the moment of minting. This ensures that only fees generated after a holder’s deposit are credited to that holder, preserving the intended proportional revenue sharing.
