# CM can `delegatecall` to any address and bypass all restrictions

## Description

The [`GuardCM`](https://github.com/code-423n4/2023-12-autonolas/blob/main/governance/contracts/multisigs/GuardCM.sol) contract is designed to restrict the Community Multisig (CM) actions within the protocol to only specific contracts and methods. This is achieved by implementing a [`checkTransaction()`](https://github.com/code-423n4/2023-12-autonolas/blob/main/governance/contracts/multisigs/GuardCM.sol#L387) method, which is invoked by the CM `GnosisSafe` [before every transaction](https://github.com/safe-global/safe-contracts/blob/186a21a74b327f17fc41217a927dea7064f74604/contracts/GnosisSafe.sol#L147-L167). When `GuardCM` is not paused, the implementation restricts calls to the `schedule()` and `scheduleBatch()` methods in the timelock to only specific targets and selectors, performs additional checks on calls forwarded to the L2s and blocks self-calls on the CM itself, which prevents it from unilaterally removing the guard: ```solidity if (to == owner) { // No delegatecall is allowed if (operation == Enum.Operation.DelegateCall) { revert NoDelegateCall(); } // Data needs to have enough bytes at least to fit the selector if (data.length < SELECTOR_DATA_LENGTH) { revert IncorrectDataLength(data.length, SELECTOR_DATA_LENGTH); } // Get the function signature bytes4 functionSig = bytes4(data); // Check the schedule or scheduleBatch function authorized parameters // All other functions are not checked for if (functionSig == SCHEDULE || functionSig == SCHEDULE_BATCH) { // Data length is too short: need to have enough bytes for the schedule() function // with one selector extracted from the payload if (data.length < MIN_SCHEDULE_DATA_LENGTH) { revert IncorrectDataLength(data.length, MIN_SCHEDULE_DATA_LENGTH); } _verifySchedule(data, functionSig); } } else if (to == multisig) { // No self multisig call is allowed revert NoSelfCall(); } ``` However, a critical oversight in the current implementation allows the CM to perform `delegatecall`s to any address but the timelock. As can be seen above, `DelegateCall` operations are only disallowed when the target is the timelock (represented by the `owner` variable). What this effectively means is that the CM cannot run any `Timelock` function in its own context, but it can `delegatecall` to any other contract and hence execute arbitrary code. This allows it to trivially bypass the guard by delegating to a contract that removes the guard variable from the CM’s storage. The CM holds all privileged roles within the timelock, which is in turn the protocol’s owner. This means that the CM can potentially gain unrestricted control over the entire protocol. As such, this vulnerability represents a significant risk of privilege escalation and is classified as high severity.

## Derived Narrative

The following field is derived content and may not be source-grounded:

The GuardCM contract is intended to act as a transaction filter for the Community Multisig (CM) by checking each outgoing call in the GnosisSafe before it is executed. The checkTransaction function explicitly rejects delegatecall operations only when the destination address equals the timelock owner, assuming that the timelock is the only place where delegatecall could be dangerous. Because the guard does not verify the operation type for any other target address, the CM can issue a delegatecall to an arbitrary contract. An attacker can deploy a small contract that contains a function which writes zero to the storage slot that holds the guard address inside the safe, effectively deleting the guard. By submitting a transaction that delegatecalls this malicious contract, the guard variable is cleared, after which the CM is free to invoke any timelock function such as schedule or scheduleBatch without restriction. The vulnerability is triggered whenever the guard is active (not paused) and the CM submits a transaction with Enum.Operation.DelegateCall to a non‑owner address. The impact is a privilege‑escalation path that allows the CM, which already holds the privileged role in the timelock, to remove the only remaining safeguard and gain unrestricted control over protocol functions, potentially leading to unauthorized fund transfers, treasury pauses, or other state changes that violate the protocol’s business logic. The issue was discovered during a Code4rena audit by adding a test that performs a delegatecall to a contract that clears the guard storage slot; the test showed that a previously reverted schedule call becomes successful after the guard is removed. The bug is subtle because the guard appears to enforce strict target and selector checks, yet the missing generic delegatecall prohibition is easy to overlook in code review. From a user perspective the symptom is that a transaction that should be blocked (for example a call to pause the treasury) suddenly succeeds, and the UI may show that the guard address is now zero or missing. The vulnerability belongs to the class of “improper access control via unchecked delegatecall” and violates the assumption that only the timelock needs protection from delegatecall. The recommended fix is to reject all delegatecall operations regardless of the target address, or to add an explicit check that the operation is not DelegateCall before any other logic, thereby eliminating the bypass vector.
