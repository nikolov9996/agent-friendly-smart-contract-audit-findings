# Malicious MarketHelper contract can be used

## Description

User-supplied marketHelper contract is called for building market's execute() call, but in leverageUpReceiver() and marketRemoveCollateralReceiver() it's not whitelisted. An attacker can craft any logic and provide it as marketHelper, placing arbitrary modules and calls for market execute(), not corresponding for buyCollateral or removeCollateral operations. For example, removeCollateral operation can have both msg_.withdrawParams.withdraw == true and to = msg_.user instead of to = msg_.removeParams.magnetar, stealing the corresponding assets from magnetar balance (i.e. instead of forwarding the user assets received it will use assets from the own balance instead as user both received assets directly and called withdraw via magnetar). In the example above magnetar, being a helper contract itself, has to have assets on the balance to steal. But there might be different sequences of operations allowing other loss making manipulations. Placing to medium the cumulative probability of reaching the state when crafted marketHelper produced call sequence can trick the desired logic to gain a material benefit. ## Derived Narrative

The following field is derived content and may not be source-grounded:

The vulnerability originates from the fact that the marketHelper contract address supplied by a user is used to build the call data for a market's execute() function without being verified against the protocol's whitelist in two receiver functions: leverageUpReceiver() and marketRemoveCollateralReceiver(). Because the whitelist check is missing, an attacker can deploy a malicious marketHelper that returns arbitrary module identifiers and calldata sequences. When the receiver forwards these modules and calls to the market's execute() method, the market will perform the attacker‑controlled actions. In a typical exploit scenario the attacker crafts a marketHelper whose removeCollateral() implementation encodes a call that directs the withdrawn assets to the attacker’s address instead of the intended magnetar contract. The receiver then approves the market to spend the specified share, invokes the malicious marketHelper, and the market executes the forged call, causing assets that should have been returned to the user or held by the protocol to be transferred to the attacker’s balance. This can happen whenever a user includes a custom marketHelper in a leverage‑up or collateral‑removal request, and the protocol relies on the assumption that marketHelper contracts are benign and follow the standard interface. The impact is severe: funds can disappear from the protocol’s accounting, users may receive no collateral or a zero withdrawal, and the protocol’s financial integrity is compromised. The issue is difficult to detect because the returned calldata is opaque; the contract simply forwards whatever the marketHelper provides, and there is no explicit validation of the destination address or the semantics of the called functions. The bug belongs to the class of unchecked external contract calls and insufficient input validation, specifically missing whitelist enforcement for auxiliary helper contracts. To remediate, the protocol should extend the existing whitelist verification to include the marketHelper address in both leverageUpReceiver() and marketRemoveCollateralReceiver(), ensuring that only approved helper contracts can supply call data. Alternatively, the protocol could validate the structure and intent of the returned modules and calls, or restrict the marketHelper to a known interface that cannot be abused. By enforcing these checks, the protocol would prevent malicious marketHelper contracts from injecting arbitrary logic into market.execute(), thereby protecting user assets and preserving correct accounting.
