## Derived Narrative

The following field is derived content and may not be source-grounded:

The vulnerability originates from the way the Registry contract deploys an Anchor contract using the CREATE3 pattern provided by the Solady library. CREATE3 creates a two‑step deployment: first a minimal proxy contract is deployed, and then the actual contract bytecode is placed behind that proxy. The Anchor constructor was written under the assumption that the Registry contract itself would be the direct caller (msg.sender) during construction, and it stores msg.sender as the reference to the Registry. In reality, because of the proxy, msg.sender inside the Anchor constructor is the proxy contract, not the Registry. As a result, the Anchor instance records an address that points to an empty proxy rather than the real Registry. When a profile owner later calls Anchor.execute, the function checks registry.isOwnerOfProfile(profileId, msg.sender). Since the stored registry address is the proxy, the call is forwarded to a contract that does not implement the Registry interface, causing the call to revert with UNAUTHORIZED. Consequently, the profile owner cannot perform any authorized actions through the Anchor, and any ether or tokens sent to the Anchor become irretrievable, effectively locking the funds. This bug manifests whenever Registry.createProfile is invoked, because each profile creation triggers the faulty CREATE3 deployment. It was discovered during an audit by adding a test that logged the registry address stored inside the Anchor and observed a mismatch between the expected Registry address and the actual proxy address. The issue is subtle because the deployment transaction succeeds and the Anchor address appears valid, so developers may not notice that internal calls are failing. The problem belongs to the class of constructor‑context mis‑identification bugs, where a contract incorrectly assumes msg.sender is a specific trusted contract during deployment. To remediate, the Anchor constructor should accept the Registry address as an explicit parameter and store it, while the Registry should encode this address into the creation code passed to CREATE3. This eliminates reliance on msg.sender and ensures the Anchor holds a correct reference to the Registry, restoring the ability of profile owners to execute functions and preventing permanent loss of funds.
