# Exchange rate is calculated incorrectly when

## Description

The exchange ratio between shares and assets is calculated incorrectly when the vault is closed. This can cause accounting inconsistencies, funds being stolen and users being unable to redeem shares. The functions AsyncSynthVault::_convertToAssets and AsyncSynthVault::_convertToShares both add 1 to the epoch cached variables totalAssetsSnapshotForDeposit, totalSupplySnapshotForDeposit, totalAssetsSnapshotForRedeem and totalSupplySnapshotForRedeem. This is incorrect because the function previewSettle, used in _settle(), already adds 1 to the variables: ```solidity ... uint256 totalAssetsSnapshotForDeposit = _lastSavedBalance + 1; uint256 totalSupplySnapshotForDeposit = totalSupply + 1; ... uint256 totalAssetsSnapshotForRedeem = _lastSavedBalance + pendingDeposit + 1; uint256 totalSupplySnapshotForRedeem = totalSupply + sharesToMint + 1; ... ``` This leads to accounting inconsistencies between depositing/redeeming when a vault is closed and depositing/redeeming when a vault is open whenever the exchange ratio assets/shares is not exactly 1:1. If a share is worth more than one asset: • Users that will request a deposit while the vault is closed will receive more shares than they should • Users that will request a redeem while the vault is closed will receive less assets than they should When the ratio between shares and assets is not 1:1 the protocol calculates the exchange rate between assets and shares inconsitently. This is an issue by itself and can lead to loss of funds and users not being able to claim shares. It can also be taken advantage of by an attacker to steal shares from the claimable silo. the attacker is not required to mint any share.

## Proof of Concept

This can be taken advantage of by an attacker by doing the following: 1. The attacker monitors the mempool for a vault deployment. 2. Before the vault is deployed the attacker transfers to the vault some of the vault underlying asset (donation). This increases the value of one share. 4. Users use the protocol normally and deposits some assets. 6. Some users request a deposit while the vault is closed. 7. The attacker monitors the mempool to know when the vault will be open again. 8. Right before the vault is opened, the attacker performs multiple deposit requests with different accounts. For each account he deposits the minimum amount of assets required to receive 1 share. 9. The vault opens. 10. The attacker claims all of the deposits with every account and then redeems the shares immediately for profit. This will "steal" shares of other users (point 6) from the claimable silo because the protocol will give the attacker more shares than it should. The attacker will profit and some users won't be able to claim their shares. ## Recommendation

In the functions AsyncSynthVault::_convertToAssets and AsyncSynthVault::_convertToShares: • Return 0 if requestId == 0 • Don't add 1 to the two cached variables It's also a good idea to perform the initial bootstrapping deposit in the initialize function (as suggested in another finding) and require that the vault contains 0 assets when the first deposit is performed.

## Derived Narrative

The following field is derived content and may not be source-grounded:

The vulnerability is an incorrect exchange rate calculation between vault shares and underlying assets when the vault is in a closed state. The contract stores snapshot variables for total assets and total supply and adds a constant offset of 1 to each snapshot inside the previewSettle function. The conversion helpers _convertToAssets and _convertToShares add the same offset again, resulting in a double‑increment of the cached totals. Because the exchange ratio is derived from these snapshots, the double increment skews the ratio whenever the share‑to‑asset price deviates from 1:1. When the vault is closed, a user who requests a deposit receives more shares than the deposited assets merit, while a user who requests a redemption receives fewer assets than they are entitled to. The discrepancy accumulates in the claimable silo, allowing an attacker to deposit the minimal amount needed for one share across many addresses, claim the inflated shares after the vault reopens, and immediately redeem them for a profit, effectively stealing value from honest users. The issue appears only when the vault is closed and the exchange rate is not exactly 1:1; it does not affect operations while the vault is open or when the rate is 1:1. The bug was discovered during a manual audit that examined the accounting logic of AsyncSynthVault and identified the redundant +1 operation. It is subtle because the extra unit is small and the contract’s public view functions hide the internal snapshot values, making the mis‑balance hard to notice until a large number of deposits are processed. The impact includes accounting inconsistencies, loss of user funds, inability for users to redeem their shares, and a vector for profit‑making attacks that require no minting of new shares. The vulnerability belongs to the class of “incorrect accounting due to double counting of state variables” or “snapshot mis‑adjustment”. To remediate, the conversion functions should return zero for a zero request identifier and must not add the extra 1 to the cached totals; the snapshot should be taken only once in previewSettle. Additionally, initializing the vault with a zero‑balance deposit and enforcing a zero‑asset balance before the first real deposit can prevent the offset from being applied on an empty vault. From a user perspective, a depositor may see that they receive more shares than expected, while a redeemer may notice that the amount of assets returned is lower than anticipated, sometimes even zero, leading to confusion and loss of confidence.
