# Incorrect handling of first deposit for new module

## Description

See detail. (uint256 _amt0, uint256 _amt1) = pool.getReserves(); if (!notFirstDeposit) { if (_amt0 > 0 || _amt1 > 0) { // #region send dust on pool to manager. address manager = metaVault.manager(); alm.withdrawLiquidity(_amt0, _amt1, manager, 0, 0); // #endregion send dust on pool to manager. } _amt0 = _init0; _amt1 = _init1; notFirstDeposit = true; } This code assumes that the reserves of the pool (_amt0, _amt1) will be dust amounts. The case that the protocol did not consider: This module could be a new module that was set via ArrakisMetaVault.setModule(). When setModule() is called, it withdraws all the liquidity through the old module: _module.withdraw(module_, BASE); // BASE means withdraw 100% of the liquidity // the new module (module_) is the receiver of the liquidity (_module is the old module, and module_ is the newly set one) Then, all the funds are directly transferred to the new module, and initializePosition is called to deposit it into the pool. This issue is that the notFirstDeposit boolean is still false, indicating that the first deposit has not yet occured. Then when the first deposit occurs in the module, the ‘dust removal’ logic shown earlier is triggered in the the new module. However all the liquidity from the old module has been deposited via the new one. This means that _amt0 and _amt1 will not be dust, as they represent the entire liquidity of the pool. Then, as shown in the PoC, the ‘dust removal’ logic withdraws the entire liquidity of the pool, and sends it to the manager of the meta vault (ArrakisStandardManager). So far, while this is already a severe error, it’s not all bad since the owner of ArrakisStandardManager is trusted, and they can withdraw the funds via withdrawManagerBalance() and return the funds so that users don’t lose any funds. However, it gets even worse, because a malicious executor can DOS the withdrawManagerBalance() function for that specific vault. There is a PoC for the • Malicious executor calls ArrakisStandardManager.rebalance(), with malicious payload • It ends up calling pool.setPoolManager(address(0)) • Now pool.claimPoolManagerFees() will revert since the ValantisHOTModule is no longer the pool manager • Hence, withdrawManagerBalance() will revert since it requires pool.claimPoolManagerFees() to be called via the module. pool to make the managerFee variable non-zero so that the expectedMinReturn passed in to within ValantisHOTModule.swap() of 1 can be met. (see PoC to understand) 100% of the pool liquidity is lost after the first deposit occurs in a new module. It is sent to the ArrakisStandardManager. The value of everyone’s shares in the vault goes to effectively zero. Then due to the DOS by the malicious executor, the funds cannot be withdrawn from the manager by calling withdrawManagerBalance(vault). The only way would be to deploy an entirely new vault with the same token0 and token1, and then calling withdrawManagerBalance(newVault) to collect the tokens from the ArrakisStandardManager contract.

## Derived Narrative

The following field is derived content and may not be source-grounded:

An incorrect handling of the first deposit in a newly‑installed module allows the entire liquidity of the Arrakis pool to be withdrawn to the ArrakisStandardManager. The contract code assumes that when the flag notFirstDeposit is false the reserves returned by pool.getReserves() are only dust left after a previous withdrawal. When a new module is set via ArrakisMetaVault.setModule, the old module withdraws all liquidity and transfers it to the new module, which then calls initializePosition to deposit the full amount. Because the boolean notFirstDeposit is never reset, the first deposit logic treats the full reserves as dust and executes the dust‑removal branch, calling alm.withdrawLiquidity with the full reserve amounts and sending the tokens to the manager. Consequently the pool becomes empty, the vault’s share value drops to near zero and users receive no tokens for their deposits. The issue was discovered during a functional audit that exercised module replacement and observed that the manager balance increased by the full pool amount after the first mint. The bug is subtle because the code path is only exercised after a module change, a scenario that is not covered by typical tests, and the manager is a trusted contract, so the loss is not immediately obvious. An attacker can further exploit the situation by calling ArrakisStandardManager.rebalance with a payload that sets the pool’s manager to address(0). This causes pool.claimPoolManagerFees to revert, which in turn makes withdrawManagerBalance revert, preventing the trusted manager from returning the funds. The result is a denial‑of‑service that locks the withdrawn liquidity forever unless a new vault is deployed and the manager manually recovers the tokens. The vulnerability belongs to the class of “incorrect initialization state handling” and “assumption‑based fund routing” bugs, where state variables are not reset after a contract upgrade, leading to mis‑classification of legitimate balances as dust. To fix the issue the code must reset or correctly initialize the notFirstDeposit flag when a new module is installed, and the dust‑removal logic should verify that the reserves are indeed negligible before withdrawing, or be disabled for the first deposit after a module change. Additionally, the manager‑withdrawal flow should be hardened against reverts caused by pool manager changes, for example by separating fee collection from the manager balance recovery or by protecting the manager address from being set to zero.
